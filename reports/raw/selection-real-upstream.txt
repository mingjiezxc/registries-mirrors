真实上游并发探测实测 —— s5 的原始读数（独立于被测代码）
========================================================================

【执行环境】主机 192.168.188.101（开发机 / SASE 网关），Go 1.27，出口代理
HTTP_PROXY=HTTPS_PROXY=http://192.168.188.1:3128（`source scripts/env.sh`）。
本任务只读网络，未接触 192.168.188.103 上的任何容器或配置。
注意：本文件所有数字来自 101 的出口路径；103 的出口路径可能不同，
103 上的耗时排序需在 103 上另跑一次，不能把这里的排名直接搬过去。

【被测对象】抉择器的探测行为：对每个候选上游并发发
HEAD <upstream>/v2/<repo>/manifests/<ref>，User-Agent: rms/selection-probe，
单个探测超时 10s（namespaces.selection.probe_timeout 的默认值），
401 时按 WWW-Authenticate 取 Bearer token 重试一次，2xx 才算「存在」。

【程序】两个独立小程序，**都不 import rms 任何内部包**（避免与被测代码同源）：
  .probe/selection/main.go          并发整轮探测，产出逐次读数与并发压缩比
  .probe/selection/tokenwalk/main.go 单条认证路径逐步走（HEAD#1 → token → HEAD#2）

  重跑：
    source scripts/env.sh
    go run .probe/selection/main.go -mode=proxy  -rounds=3 -out .probe/selection/raw-proxy.jsonl
    go run .probe/selection/main.go -mode=proxy  -rounds=3 -noaccept -out .probe/selection/raw-noaccept.jsonl
    go run .probe/selection/main.go -mode=direct -rounds=3 -out .probe/selection/raw-direct.jsonl
    go run .probe/selection/tokenwalk/main.go -case=both -rounds=3 -mode=proxy > .probe/selection/tokenwalk-proxy.txt
    python3 .probe/selection/mkreport.py

【规模】main 程序：6 候选 × 4 组目标 × 3 轮 × 2 种出网设置 = 144 次探测；
tokenwalk：11 个 (候选,仓库) 组合 × 3 轮 = 33 条完整认证路径。
  - shared        : 所有候选都问 library/alpine:latest（无限定名的真实场景）
  - shared-absent : 所有候选都问 library/definitely-does-not-exist-rms-probe:latest
  - native        : 每个候选问一个**确实存在于它自己上面**的仓库
                    (docker.1ms.run & registry-1.docker.io: library/alpine；
                     ghcr.io: astral-sh/uv；gcr.io: distroless/static；
                     quay.io: prometheus/busybox；registry.k8s.io: pause:3.9)
  - native-absent : 每个候选问同前缀下的不存在仓库
  native / native-absent 是判别力的对照实验：如果只有 Docker Hub 那两组能测出
  「存在」，就无法排除「非 Hub 候选恒被判 absent」的伪结论。

【表里 token 列的含义】`-` = 没有走到 token 流程（首个 HEAD 不是 401，或探测
在传输层就断了）；`T200` = 调用了 token 端点且它回 200；`T403` = 调用了 token
端点但被它 403 拒了（此时 **没有** 拿到 token，也就没有 HEAD#2）。这个区分很
重要：`token_flow=false` 只说明「没拿到票」，不说明「没去取票」。


========================================================================
一、结论（先看这一段）
========================================================================

1) 判别力成立：6 个候选在 native 组**都** 3/3 轮返回 2xx 被判 exists，
   在 native-absent 组都判 absent（tokenwalk 的 contrast 组逐条复核过：
   ghcr.io/astral-sh/uv、gcr.io/distroless/static、quay.io/prometheus/busybox、
   registry.k8s.io/pause 全部 200）。三类结果在实测里都被真实触发：
   - 存在   = 2xx
   - 不存在 = 404 或 403（认证走完后）
   - 不可达 = 传输层错误 / 超时 / **认证没走通**（见第 6 条与第五节）

2) 同一个无限定名在不同候选上的判定确实不同，这正是抉择器要利用的信号：
   proxy 模式 shared 组 3/3 轮一致 —— library/alpine 只有 Docker Hub 系两个候选
   判 exists（200），ghcr.io / gcr.io / quay.io 判 401、registry.k8s.io 判 404。

3) 并发压缩比：一轮里 6 个探测的发出时刻极差（spread）中位 0.15ms、
   最大 0.4ms（proxy，direct 最大 0.5ms），几乎同时出发。
   以「串行耗时之和 ÷ 实际墙钟」计的压缩比：
     proxy  2.80x ~ 4.68x（中位 3.53x）
     direct 3.00x ~ 4.25x（中位 3.80x）
   串行对照：proxy 一轮 6 次探测合计中位 15.4s → 并发后墙钟中位 4.3s；
   direct 合计中位 37.4s → 并发后中位 10.0s。
   注意分子分母的口径：串行之和用的是**总耗时**（含 token 往返），墙钟用的是
   整轮真实墙钟，所以比率略低于「候选数 6」。

4) 10s 的 probe_timeout 是**天花板而不是余量**：本批次 proxy 12 轮里 0 轮、
   direct 12 轮里 9 轮墙钟打满 10001ms（direct 更容易顶到上限，因为直连更慢、
   超时更多）。未命中缓存时，一次无限定请求的等待上限确实由 probe_timeout 决定
   （与配置口径一致），而它**真的会被用满**。

5) 走代理 vs 直连是**两个方向都有**的差异：
   - 对国内镜像 docker.1ms.run，直连快得多（native 组中位
     1812ms 走代理 vs 449ms 直连，
     约 4.0 倍），走代理是负优化；
   - 对海外上游直连要么更慢要么直接失败：registry-1.docker.io 直连 12 次里
     2 次 unreachable、走代理 0 次，
     直连原文含 `read tcp ...:443: read: connection reset by peer` 与 `context deadline exceeded`；
     quay.io 直连也有 2 次 unreachable（走代理 0 次）。
   - token 流程成功率同步变化：proxy 51/72 次探测走到了 token 端点、
     36 次拿到票；direct 分别为 49/72 与 26 次。

6) **认证路径的三态**（Lead 追问的口径问题，逐条读数在第五节）：对
   library/alpine:latest，6 个候选分成三类，而不是「都是 401」：
     docker.1ms.run        401 → token 200 → HEAD#2 200   存在
     registry-1.docker.io  401 → token 200 → HEAD#2 200   存在
     ghcr.io               401 → token **403**，拿不到票   认证未走通
     gcr.io                401 → token **403**，拿不到票   认证未走通
     quay.io               401 → token 200 → HEAD#2 **401** 认证未走通
     registry.k8s.io       **404**（根本没有挑战）         明确不存在
   这意味着：如果把「401/403 → absent（404）」当成一条铁律，ghcr.io / gcr.io /
   quay.io 三个上游的**认证故障**会被读成「明确没有这个镜像」。ghcr.io 的对照
   读数说明这不是「上游整体坏了」而是**按仓库拒绝**（同一时刻 astral-sh/uv 的
   token 端点 3/3 次回 200、HEAD#2 3/3 次 200），但它仍然是「权限判决」而不是
   「存在性判决」——私有的同名仓库会得到同样的 403。是否把这一态并入 absent
   是 dispatcher 的设计选择，本文件只给读数：**这一态不是 404 的证据**。

7) 一个必须在设计里承认的限制：对 ghcr.io / gcr.io，「不存在」与「存在但私有」
   在匿名探测下无法区分（都是 token 端点 403）；对 quay.io，拿到票之后仍 401
   同样无法区分「不存在」与「无权限」。而 Docker Hub 反过来：不存在的仓库回
   401 而不是 404（shared-absent / native-absent 里 registry-1.docker.io 3/3 轮
   都是 401(T200)）。所以「401 → absent」对 Hub 是必需的，对其它上游则过宽。

8) 内容协商对照（补测，第八节）：本文件的探针**默认就带** 4 个 manifest media type 的
   Accept（.probe/selection/main.go 的 acceptHeaders，第 91 行），所以第二至七节的读数
   本来就是「带 Accept」那一列。为了回答「那些 401/404 会不会是内容协商造成的假 absent」，
   另用 -noaccept 跑了第二遍：按 (组, 候选) 逐格比对两遍的状态，**有 6 格翻转**（ghcr.io 与 gcr.io 两个候选 × native 组 3 轮 = 6 格；两边合计 12 组 × 6 候选 × 2 遍 = 144 个观测（.probe/selection/raw-proxy.jsonl 与 raw-noaccept.jsonl 各 12 条记录 × 每条 6 个候选，复算得 72+72=144），翻转 6 格）——
   ghcr.io 与 gcr.io 的 native 组各 3 轮都从 200 变 404（早先本节写作「只有 2 格」，与逐轮表不符，
   2026-10-13 按 raw-proxy.jsonl 与 raw-noaccept.jsonl 逐格复算更正为 6 格）；`library/alpine` 相关的每一格两遍**完全一致**。所以那些
   ghcr.io/gcr.io/quay.io 的 401 与 registry.k8s.io 的 404 是**认证判决**，不是内容协商假象。
   翻转的那 6 格（2 个仓库 × 3 轮）恰好就是 rms 抉择器（不带 Accept）会把**存在的**镜像判成不存在的那种情形。

5.4 耗时口径（Lead 第 4 问）
  二/三节的 `duration_ms` 是**一次完整探测的总耗时**，即

  以 proxy round1 shared 的三个候选为例（同一次运行里逐段拆出来的）：
    docker.1ms.run        head1 2022.5ms + token 1175.4ms + head2 3131.2ms = 6329.3ms（实测 6329.3ms）
    registry-1.docker.io  head1 3370.0ms + token 2866.0ms + head2  568.4ms = 6804.5ms（实测 6816.5ms）
    quay.io               head1 1267.2ms + token  298.6ms + head2  746.4ms = 2312.2ms（实测 2312.4ms）
    ghcr.io               head1 3930.3ms + token  361.0ms + head2    0.0ms = 4291.4ms（实测 4291.4ms）
  （两处小差额是段间 Go 侧记账开销；表里的 duration_ms 是端到端实测值。）
  jsonl 里同时保留 head1_ms / token_get_ms / head2_ms / token_status，
  报告与复核都可以只用其中一段，不必依赖总和。
  这也解释了为什么 token 端点的往返**计入**抉择器的 ProbeLatency 比较：
  两个都存在的候选里，谁的 token 往返慢，谁就排在后面。若设计上希望只比较
  「首个 HEAD 的 RTT」，需要用 head1_ms 而不是 duration_ms —— 这是一个
  明确的口径选择，本文件同时给出两列供 dispatcher 决定。

八、补测(2026-10-13 追加):内容协商对照 —— 带 / 不带 manifest Accept
========================================================================

起因:rms 的抉择器(internal/selection/probe.go)构造探测请求时只设了 User-Agent,没有设
manifest 的 Accept;而 e2e 用例在一个**冷缓存**上请求一个确实存在的镜像时拿到 404
NAME_UNKNOWN,假上游日志给出原文:

    "err.message":"OCI manifest found, but accept header does not support OCI manifests",
    "http.request.method":"HEAD","http.request.useragent":"rms/selection-probe",
    "http.response.status":404

要判定的问题:本文件前面那些「ghcr.io/gcr.io/quay.io 对 library/alpine 判 401/404」的读数,
到底是仓库真的不在,还是内容协商挡出来的**假 absent**?

做法:同一个探针程序(.probe/selection/main.go,它**本来就带** 4 个 manifest media type 的
Accept,见该文件 acceptHeaders),加一个 -noaccept 开关跑第二遍;两遍**只差这一个请求头**,
都是走代理、每个组合 3 轮、同一批次背靠背跑完。命令:

    go run .probe/selection/main.go -mode=proxy -rounds=3             -out .probe/selection/raw-proxy.jsonl      # 带
    go run .probe/selection/main.go -mode=proxy -rounds=3 -noaccept   -out .probe/selection/raw-noaccept.jsonl   # 不带

8.3 结论:两类 absent 必须分开写

  (a) 认证判决类 absent —— 与 Accept 无关。ghcr.io / gcr.io 对 library/alpine 的 401 来自
      **token 端点 403**(拿不到票),quay.io 的 401 来自**拿到票后 manifest 仍 401**,
      registry.k8s.io 的 404 是**根本没有挑战直接 404**。这些读数在两遍里**逐格一致**,
      所以它们不是内容协商造成的假 absent。401 也不可能由 Accept 产生:
      内容协商失败的表现是 404(见 (b)),不是 401。
  (b) 内容协商类**假 absent** —— 只在**仓库真的存在**于 ghcr.io / gcr.io 且客户端不带
      manifest Accept 时出现:本批次里 native 组(ghcr.io 的 astral-sh/uv、gcr.io 的
      distroless/static)从 **200 翻成 404**(3/3 轮)。这正是 rms 抉择器现在的处境:
      它会把这两个 namespace 上**存在**的镜像判成不存在。
      注意 docker.1ms.run、registry-1.docker.io、quay.io、registry.k8s.io 在 native 组
      两遍都是 200 —— 它们宽容,少一个 Accept 头也不影响。

  所以对 Lead 的问题的直接回答:**表里那 22 个「ghcr.io 401 / gcr.io 401 / quay.io 401 /
  registry.k8s.io 404」的格子不是内容协商假象** —— 两遍完全一致;而且它们全是 401/404-without-
  challenge 这类认证判决。(b) 类只影响 native 组那两格,也正好就是 e2e 抓到的那条缺陷。

  范围限定:HEAD 响应没有 body,所以 (b) 的签名消息只出现在**上游自己的日志**里(见上面的
  原文),抓不到响应体;本文件因此用「同一仓库 200 → 404 的状态翻转」作为判据,而不是靠消息文本。
  另外本地缓存先于探测被查(internal/selection «cachedOnDisk»),热缓存不受 (b) 影响,
